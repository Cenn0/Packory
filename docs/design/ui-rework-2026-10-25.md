# Packory UI Rework — Product Design Specification

**Status:** Design proposal, not implemented in the Packory runtime.
**Date:** 2026-10-25
**Source baseline:** Packory `main` as reviewed on 2026-10-24; AiSet `7731c8b60df81fbec73828d83295a8df27eba6e1`.
**Privacy:** Public-repository-safe content only. Synthetic examples, no personal contact data, secrets, private branding or private AiSet implementation files.

## 1. Purpose and boundaries

Packory is a self-hosted multi-registry for software packages, OCI artifacts, agent skills, MCP registry metadata and related distributable content. It is **not** a Git forge, CI platform or generic proxy.

The existing UI in `src/Packory/wwwroot/{index.html,style.css,app.js}` combines catalog discovery, feed endpoints, skill import and inspection, MCP and configuration in one long page. The rework separates frequent catalog use from feed administration and high-risk review operations. Existing Packory identity and `src/Packory/wwwroot/brand/packory.svg` must **not** be replaced.

This file is the product-specific design specification. AiSet remains the canonical source for the generic methodology; do **not** copy private AiSet templates or unrelated brand assets into this public repository.

## 2. Target users and top tasks

| Role | Main task | Expected outcome |
| --- | --- | --- |
| Package consumer | Find package or skill, choose a version, obtain protocol-specific usage instructions | Correct package/version/feed context and copyable command |
| Feed maintainer | Configure and inspect hosted or upstream feeds | Verifiable scope, endpoints and lifecycle |
| Skill reviewer | Inspect static findings, optional AI findings and exact artifact digest before deciding | Auditable, authorization-checked decision over an immutable identified version |
| Instance administrator | Maintain identity, access and configuration | Transparent settings and change outcome |

Assume desktop keyboard/mouse for administration and review, with responsive, functional mobile browsing. This is a design assumption, not user research.

## 3. Information architecture

Primary navigation, in this order:

1. **Catalog** — initial route; all supported artifact types, filtering, package/skill details, version history, compatible commands, MCP metadata as an explicit content type.
2. **Feeds** — feed list, protocol, scope, endpoint, state and creation/edit details. Hosted/private feeds and upstream/global caching must be distinguished.
3. **Reviews** — review queue and detailed static/AI findings, digest, policy, decision and audit evidence.
4. **Activity** — scoped audit and operational events with timestamp, object and outcome.
5. **Settings** — instance configuration, identity/access (permission-gated), optional AI inspection settings.

Avoid creating one menu entry per backend endpoint. Object actions appear next to their objects. The active route, selected feed and active filters remain visible. Persist filter/query context through detail navigation and browser back; use meaningful deep links, not DOM-only hidden panels.

**Evaluated alternative:** A feed-first home screen better suits feed operators but makes cross-ecosystem package discovery secondary. Choose catalog-first for a unified distribution hub; expose feed-specific navigation inside the Feed area.

## 4. Characteristic screens

### Catalog — `/catalog`

- Top: title **Catalog**, a search input and a narrowly scoped **Filter** control.
- List/table is the primary presentation, not large interchangeable cards. Rows prioritize **name**, **ecosystem**, **version**, **source/feed**, **release or observed timestamp** and **availability/verification status** (only where reliably supplied).
- Query scope explicitly tells users what was searched; search must not leak inaccessible feed names.
- Filter by ecosystem and feed; retain results state on return from details.
- No results: “No packages match these filters.” with **Clear filters**.
- Data unavailable: “The catalog could not be loaded.” with an appropriate diagnostic/retry, never “No packages”.
- Separate last-known/cached metadata from confirmed current availability.

### Package detail — `/catalog/{type}/{identifier}`

- Identity header: package name, exact source/feed, selected version and ecosystem.
- Versions table; package-specific usage/install instructions based on selected manager, feed and version.
- Copy button reports success **only after** clipboard writes succeed. Fallback: selectable complete command.
- Long identifiers and commands wrap or horizontally scroll **within** the component without page-level overflow.
- Integrity digest, provenance, policy or verification badges only when supported by actual records; do not infer trust from mere presence in the catalog.
- MCP registry entries show metadata and discovery information without suggesting Packory executes the server.

### Feeds — `/feeds`, `/feeds/{id}`

- Compare feed name, protocol, kind (hosted/upstream), scope, explicit lifecycle and endpoint.
- Editing uses a grouped form with visible labels and validation.
- The actual server-confirmed state is distinguishable from the requested change.
- When upstream is unavailable, display last-known timestamp and data provenance; do not silently imply the feed is current.
- Sensitive actions require a clear affected-object summary and server-authorized outcome.

### Reviews — `/reviews`, `/reviews/{id}`

- Desktop master-detail: queue left, selected case right; mobile uses a list-to-detail route.
- Header always displays **skill identifier**, **version**, **digest**, **source** and **report revision** (if supported).
- Separate: **static assessment**, **optional AI assessment**, **human decision**. Never use one overall green result to imply all three have passed.
- AI assessment is opt-in and disabled by default. Show provider/model, status and provenance where known. AI text is advisory; it cannot silently authorize a release.
- Review actions require actual permission; concealment of controls is not authorization.
- Confirmations describe the exact object, version, consequences and reason.
- Approval/rejection must be based on an immutable snapshot or optimistic concurrency contract to prevent approving a report that changed after review. **API work needed if not already enforced.**
- Quarantine and scan-error scenarios must respect the real configured policy and must not visually imply successful approval.
- Explicitly distinguish “requested”, “accepted”, “running”, “completed”, “failed”, “quarantined” and “approved” as applicable.

### Activity — `/activity`

- Event rows with timestamp (timezone available), object/scope, actor where authorized, action and actual result.
- Filters by action and object. Unknown or delayed data remains visibly unknown or delayed.
- Never expose credentials, personally identifying values or secrets in public demo data, URL parameters or console output.

### Settings — `/settings`

- Group by instance, authentication/authorization and optional skill inspection; do not display all developer flags as a single form.
- Configurable AI options (when APIs support them): enabled state, provider/model, scan mode, and spending limit.
- API connection checks and save operations have distinct progress/error/confirmed states.
- Server remains authoritative for access and feature availability.

## 5. Visual system

Retain the checked-in Packory logo and existing brand identity. No borrowed HanseShield, Sentelsen or Verikeel brands. No arbitrary “AI dashboard” hero, fictional metrics, floating decorative cards, glass effects or blanket gradients.

- **Layout:** desktop compact persistent left navigation plus content; mobile accessible menu/drawer and content-first hierarchy.
- **Information density:** medium-to-high for catalog/version tables; ample target sizes in forms, touch and confirmations.
- **Typography:** legible system/UI sans for prose, stable/tabular numerals for version/timestamp columns, monospace **only** for commands, identifiers and digests.
- **Surfaces:** primarily flat surfaces and restrained dividers; depth reserved for dialogs and overlays.
- **Color:** map brand/action, selection, informational, warning, danger, success and **unknown** to separate semantic tokens. State never depends on color alone.
- **Shape:** restrained control and panel radii rather than one card style for every object.
- **Icons:** consistent stroke weight and semantic purpose. Accompany ambiguous icons with labels/tooltips.
- **Motion:** only functional interaction feedback; respect `prefers-reduced-motion`.
- **Light/dark:** both modes supported using semantic variables, not duplicated ad-hoc CSS. Theme semantics must remain identical.

Suggested CSS custom-property roles (specific values are implementation tokens to confirm against original branding):
`--surface-page`, `--surface-panel`, `--surface-raised`, `--text-primary`, `--text-muted`, `--border-subtle`, `--action-primary`, `--status-warning`, `--status-danger`, `--status-success`, `--status-unknown`, `--focus-ring`.

## 6. Interaction and state contract

Each route must cover, where relevant:

| State | Required user understanding |
| --- | --- |
| Loading | What is being loaded; no fake empty result |
| Empty | Successfully loaded collection has no records |
| No matches | Current filters exclude all matches; clearable |
| Unavailable / offline | Source could not be queried; last known data clearly marked |
| Unauthorized | Action/visibility unavailable without revealing protected details |
| Validation error | Field, rule and correct next step |
| Concurrency conflict | The viewed version changed; must review before submitting |
| Async pending | Request acceptance is not completion |
| Confirmed | Precise server-confirmed result, not assumed effect |

Avoid unverified “Saved”, “Published”, “Secure” or “Approved” claims. Repeated retries of non-idempotent actions must be designed with the corresponding API rather than a user-facing warning alone.

## 7. Accessibility and responsive behavior

Quality target: **WCAG 2.2 AA** (a goal, not a claim of certification). Verify keyboard order, focus visibility/non-obscuration, control naming, semantic tables and forms, announcements of async/error states, color contrast, zoom/reflow at 320 CSS px and narrow mobile/tablet/desktop widths. Touch targets should generally aim for 44×44 CSS px where practical. Preserve a horizontal scroll region only where genuine two-dimensional tabular data requires it. Test screen reader flows manually and with automated tools. Use responsive state tests, not just screenshots.

## 8. Proposed implementation sequence

**Package A — Shell and identity:** extract current page into the five routed work areas without breaking existing endpoints; preserve logo, public branding, keyboard access and theme. Provide route-level smoke tests.

**Package B — Catalog and package details:** connect real catalog queries and protocol-specific/version-specific guidance; support scoped search, pagination and proper error/empty states. Backend API may need aggregated listing and permission-aware search.

**Package C — Feeds and permissions:** build feed administration against actual authorization and explicit lifecycle. Ensure backend state is the authority.

**Package D — Reviews and optional AI:** migrate existing SkillSpector controls into dedicated review UX; bind decisions to exact report version/digest, server-authorized policy, and audit outcomes. Do not treat an AI suggestion as approval.

**Package E — Activity, settings, hardening:** add operational events, context-rich settings, accessibility and visual regression checks, security review and documentation.

Each package needs `dotnet test`, relevant frontend/browser assertions, current CI checks and a container-build/smoke test appropriate to its scope before merger.

## 9. Acceptance scenarios

1. Find a NuGet package, change version, copy an accurate client command and return with query/filter preserved.
2. Repeat for npm; long scoped names, identifiers and commands do not overflow mobile.
3. See no-results, loading and offline as three distinguishable situations.
4. An unprivileged visitor never obtains protected feed metadata or review actions, including via direct API invocation.
5. Open a quarantined skill; static findings, optional AI findings and decision history are visibly separate; prohibited approval is blocked by the backend.
6. A reviewer receives a stale report/version conflict and cannot approve without re-reviewing the current revision.
7. Theme and 320/390/768/1440 CSS-px layouts remain usable at increased text size with accessible keyboard focus.
8. All UI confirmation messages correspond to recorded, server-verified action outcomes.

**All scenarios are specified, not executed against the live product.** The standalone design prototype previously had separate synthetic browser checks; those checks must not be substituted for actual Packory integration tests.
