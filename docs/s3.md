# S3-compatible object storage (single-writer; restricted readers)

Packory supports a selectable filesystem or S3 artifact backend. PostgreSQL
and S3 can be combined, but **this does not make Packory horizontally scalable**.
In-process locks and OCI upload staging assume one active writer. Restricted
read-only instances exist, but NuGet/npm mirror reads are not permitted on readers.

## Runtime configuration

Default: `PACKORY_BLOB_PROVIDER=filesystem`. For S3:

```text
PACKORY_BLOB_PROVIDER=s3
PACKORY_S3_BUCKET=your-private-registry-bucket
PACKORY_S3_REGION=eu-central-1
PACKORY_S3_KEY_PREFIX=packory
```

For AWS S3, leave `PACKORY_S3_ENDPOINT` unset. AWS default credential
discovery supports IAM workload identity / instance roles (recommended).
For S3-compatible servers, set `PACKORY_S3_ENDPOINT=https://s3.example.test`.
If needed, specify `PACKORY_S3_ACCESS_KEY` and
`PACKORY_S3_SECRET_KEY` together through **runtime secrets only**;
do not commit them, print them, or include them in process arguments.

`PACKORY_S3_ALLOW_LOOPBACK_HTTP=true` permits **only HTTP on a loopback
S3 endpoint**, intended for local test emulators. It does not permit
plaintext HTTP to a remote server. Production deployments should use HTTPS
with a valid certificate and minimum-privilege bucket credentials.

## Persistence and integrity

- Immutable artifact keys are written with S3 conditional
  `If-None-Match: *` requests. A successful remote write is acknowledged
  before catalog metadata publication.
- Mutable upstream registry metadata is overwritten intentionally; immutable
  package bytes are never updated in place.
- Objects are prefixed with `PACKORY_S3_KEY_PREFIX`. Reads materialize
  remote objects into a local disk cache with **per-object size limits**,
  retaining compatibility with the existing native-client file-serving API.
  There is no aggregate S3-cache disk quota or automatic artifact eviction.
- An OCI blob or manifest fetched remotely is additionally checked against
  the SHA-256 digest embedded in its object key. Other ecosystems currently
  rely on upload-time integrity checks / upstream checksum validation.
- Recovery uses remote HEAD queries, not local files as the authority.
  Local unreferenced artifacts are quarantined on startup without deleting
  remote objects.
- If a process stops after local staging but before remote upload, the next
  immutable write serializes by key, checks remote absence and stages the
  current caller's bytes afresh. A leftover local cache cannot be mistaken
  for an acknowledged S3 publication or substituted for the new input.

## Safe PostgreSQL/S3 orphan reconciliation

Packory deliberately does not attempt distributed ACID transactions between
PostgreSQL and S3. **A recovery operation is opt-in and requires a single
database writer.** A PostgreSQL session-level advisory lock is held by each
Packory **writer** process using that metadata backend; specifically restricted
reader replicas do not acquire the exclusive writer lease. A second modern Packory
instance connecting to the same database fails startup instead of writing
concurrently. This is a safety guard, **not** active-active operation or
distributed fencing against uncooperative/older software.

If a publish is interrupted after its immutable S3 object is written but
before its metadata transaction commits, the durable publication intent remains
visible. Resolve it only through this procedure:

1. Stop all applications, workers and external writers targeting the PostgreSQL
   database and the Packory S3 prefix. Take a **coordinated backup** of both.
2. Start exactly one Packory process with
   `PACKORY_METADATA_PROVIDER=postgresql`,
   `PACKORY_BLOB_PROVIDER=s3` and
   `PACKORY_RECOVERY_MAINTENANCE=true`. This explicitly blocks normal package
   traffic, including all normal publish and cache writes. Readiness returns
   HTTP 503 on purpose; the admin reconciliation endpoints remain available.
3. Authenticate as administrator and inspect
   `GET /api/admin/publications/pending`. It now returns the observed
   `state` and any existing recovery-copy location for each intent.
4. For the intended artifact, send a JSON POST to
   `/api/admin/publications/reconcile` with **the exact** `key` and
   `expectedStartedAt` obtained from that inspection. Do not fabricate
   object keys or modify the database directly.
5. Reinspect. For a true orphan, Packory copies the bytes to a unique
   immutable `recovery/quarantine/...` object in the same S3 bucket and
   independently verifies its SHA-256. The evidence location, checksum and
   source ETag are recorded **transactionally in PostgreSQL before** a
   conditional S3 `If-Match` DELETE is attempted. The journal is closed
   only after the source disappears. Prepared evidence survives a crash;
   repeating the operation verifies the existing archive and completes it.
6. Verify the archive and restored package in staging. Stop recovery mode
   before restarting the normal instance, which must reacquire the writer lock.

Possible outcomes: `committed-journal-cleared`, `unwritten-journal-cleared`,
or `quarantined-recoverable`. A committed metadata reference with a missing
S3 object, conflicting ETag, corrupt archive or untrusted S3 implementation
**fails closed**, requiring manual restoration or investigation. No
user-controlled identity or credentials are written to recovery records.

**Limitations:** S3 compatibility with conditional DELETE must be confirmed
for the deployed provider; Moto CI alone does not establish third-party S3
certification. A crash before a PostgreSQL evidence entry can leave an
extra, untracked recovery copy; never apply lifecycle deletion to recovery
prefixes without an independent retention policy. DB and bucket must have
coordinated restore procedures. Reads and writes still use single-process
coordination and local OCI upload sessions; multi-node production operation
remains unsupported. Do **not** enable two active instances.

Reference: [S3 conditional deletes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-deletes.html),
[PostgreSQL advisory locks](https://www.postgresql.org/docs/current/functions-admin.html).

## Known limitations

- The cache uses synchronous materialization at the boundary of existing
  file-returning endpoints. This works for modest single-node installations
  but **is not best practice** for high-volume or low-latency object delivery.
  Direct streaming, asynchronous checksum verification for every package
  and local cache eviction are future work.
- There is **no distributed metadata/blob ACID transaction**. A crash after
  writing the S3 object but before metadata commit can leave an orphan. Durable
  publication intents and reviewed copy-and-verify quarantine cover selected
  interruptions, but not cross-store ACID, automatic replay or general garbage collection.
- No S3 multipart transfer, cross-node lock, shared OCI upload sessions,
  encryption-key lifecycle policy, automatic migration of existing filesystem
  objects, or multi-node HA.
- AWS SDK API compatibility does not guarantee every third-party
  S3-compatible server supports conditional writes. Validate provider support
  for `If-None-Match` before relying on immutability.
- To migrate an existing deployment, stop writes, arrange a verified
  object migration plus metadata snapshot, and test restores in a staging
  installation. Changing `PACKORY_BLOB_PROVIDER` alone does not migrate data.

## Tests

`/.github/workflows/s3.yml` runs an integration test using the actual
AWS SDK for .NET against Moto 5.2.3 as a local S3 API emulator.
It checks conditional immutable publishing, retrieval from a separate
cache directory (simulated restart), mutable metadata replacement,
OCI content-addressed reads and remote deletions.

This verifies the tested SDK/emulator API contract, **not** official
interoperability certification for all S3 vendors.

Primary references:
- https://docs.aws.amazon.com/sdkfornet/v4/apidocs/items/S3/TPutObjectRequest.html
- https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html

## Production release blocker

Provider-specific conditional PUT/DELETE semantics, versioning/retention, coordinated PostgreSQL/S3 snapshots and an isolated full restore drill have **not** been qualified on a chosen real S3 provider. See [release gates](release-gates.md). Emulator tests cannot close this gate.
